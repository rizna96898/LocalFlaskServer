世界を選んでから、チャットを始め、発言するまでに、画面とサーバーが何をするか。

**この文書の位置づけ**: 2026-10-12 時点のコードから書き起こした下書き。
判断がつかなかった所には **【要確認 Q番号】** を付けている（番号は [`api.md`](api.md) からの通し）。
各APIの項目と返却は [`api.md`](api.md)、ファイルの形は [`data.md`](data.md)、作りかけは [`../status.md`](../status.md) を見る。

<a id="s1"></a>

## 登場するもの

<div align="right"><a href="#top">▲ 目次へ</a></div>

| | 役割 |
|---|---|
| 画面 | LLM_CHAT_CONSOLE。ブラウザで開く |
| APサーバー | `src/app.py`（ポート5000）。画面からの呼び出しを受ける |
| モデルサーバー | `src/server.py`（ポート5001）。モデルを読み込み、文章を生成する。APサーバーだけが呼ぶ |

モデルを使う処理（記憶の生成、返答）は、APサーバーがモデルサーバーへ送って結果を受け取る。
モデルサーバーが止まっていても、世界の選択やセッションの一覧・削除など、モデルを使わない操作はできる。

<a id="s2"></a>

## 全体の流れ

<div align="right"><a href="#top">▲ 目次へ</a></div>

```
世界を選ぶ ─→ 新規チャット ─→ 発言 ─→ 発言 ─→ …
               │                        ↑
               └ 裏で初期記憶を生成      既存のセッションを開いて続きから
```

<a id="s3"></a>

## 1. 世界を選ぶ

<div align="right"><a href="#top">▲ 目次へ</a></div>

1. 画面の「世界選択」を押すと、ブラウザに保存してある世界の一覧（`world_list`）が出る。
2. 世界を選ぶと `/world_start` を呼ぶ。サーバーは、その世界のセッション一覧を返す。
3. 画面は、選んだ世界（`selected_world_id`、`selected_world_name`）をブラウザに保存し、セッション一覧を表示する。
   それまで選んでいたセッションは未選択に戻す。

サーバー側には「今どの世界を選んでいるか」という状態は無い。覚えているのは画面（ブラウザ）だけ。

<a id="s4"></a>

## 2. 新規チャット

<div align="right"><a href="#top">▲ 目次へ</a></div>

画面の「新規チャット」1回で、APIを2つ続けて呼ぶ。

<a id="s4-1"></a>

### 2-1. セッションを作る（`/chat_startup`）

<div align="right"><a href="#top">▲ 目次へ</a></div>

元データをセッションフォルダへコピーする。モデルは使わないので、すぐ終わる。

- 世界設定、登場人物の設定、キャラクターの画像をコピーする（詳細は [`api.md`](api.md)）。
- セッション一覧に1件足す。
- 画面は、返ってきたセッションIDを「選択中のセッション」としてブラウザに保存する。

<a id="s4-2"></a>

### 2-2. チャットを始める（`/new_chat`）

<div align="right"><a href="#top">▲ 目次へ</a></div>

1. 進行状態のファイル（`prepare_status.yaml`）を作る。
2. **初期記憶の生成を裏で始める**（下の「3. 初期記憶の生成」）。
3. 世界設定の `開始メッセージ` を履歴に書き、画面に返す。

裏の生成が終わるのは待たない。画面にはすぐ開始メッセージが出るが、その時点では記憶はまだできていない。

- 画面は、初期記憶ができるまで（成功でも失敗でも、終わるまで）「発言」を押せなくする。
  終わったかどうかは `/session_status` を1秒ごとに問い合わせて確かめる（下の「4. 進行状態」）。

<a id="s5"></a>

## 3. 初期記憶の生成（裏の処理）

<div align="right"><a href="#top">▲ 目次へ</a></div>

`/new_chat` が始め、別のスレッドで進む。モデルを何度も呼ぶので、時間がかかる。

<a id="s5-1"></a>

### 3-1. 世界の記憶

<div align="right"><a href="#top">▲ 目次へ</a></div>

- 材料: 世界設定の `登場人物`、`シナリオ本文` の `現在`、`開始メッセージ`
- モデルに1回送り、返ってきたYAMLを整えて `world_memory.yaml` に保存する。
- 返事が期待の形（`現在の状態` と `世界の状態` を持つ）でなければ、もう1回だけ送り直す。
- `世界の状態` → `参加者` が空なら失敗とする。

<a id="s5-2"></a>

### 3-2. キャラクターの記憶

<div align="right"><a href="#top">▲ 目次へ</a></div>

世界の登場人物のうち、`参照種別` が `character` の人物を、1人ずつ順に処理する。1人につきモデルを8種類の用途で呼ぶ。

| 順 | 段階 | やること | 結果の使い道 |
|---|---|---|---|
| 1 | 要約 | キャラクター設定・シナリオ・開始メッセージから、今の状況を箇条書きにする | 以降の段階の材料。`temp/` に保存 |
| 2 | 場所 | 要約から、今いる場所を決める | `場所` |
| 3 | 分類 | 要約の各行を「行動」「状態」「心情」に分ける | `行動`、`状態`、`心情`。`temp/` に保存 |
| 4 | 服装 | キャラクター設定から、今の服装を決める | `服装` |
| 5 | 所持品 | 服装・場所・要約から、持ち物を決める | `所持品` |
| 6 | 意識 | 開始メッセージから、今意識を向けている相手を決める | `意識` |
| 7 | 金額 | 所持金を決める | `金額` |
| 8 | 抱えている事情 | キャラクター設定・シナリオ本文・開始メッセージから、悩み・目的・秘密・大事な出来事・約束を書き出す | `抱えている事情`（`現在の状態` とは別） |

全部そろったら `character/{ID}_memory.yaml` に保存する。`関係性` には、世界の記憶の `現在の状態` → `参加者` をそのまま入れる。

- どれか1つの段階で失敗すると、そのキャラクターの記憶は保存されず、**残りのキャラクターも処理しない**。
- 各段階で使うプロンプトと生成の設定は [`prompts.md`](prompts.md)。
- 失敗した段階からのやり直しはしない。画面に失敗したこと（どこで失敗したか）を出し、新規チャットを押し直してもらう。
- 登場人物が複数いる場合も、1人ずつ順番に処理する。モデルサーバーは一度に1つしか処理できない（同時に送っても順番待ちになる）ので、
  並べても速くならないため。人数が増えて時間が気になったら、段階を減らすなどで考える。

- モデルの返事をYAMLとして読む段階（服装・所持品・意識・所持金と、発言のあとの記憶の更新）は、読めない・形が違うときだけ**1回だけ聞き直す**。
  2回とも読めなければ、その段階で失敗する。世界の記憶も、形が違えば1回だけ送り直す。
  成功している間は呼び出しが増えないので、待ち時間は変わらない。

<a id="s6"></a>

## 4. 進行状態（`prepare_status.yaml`）

<div align="right"><a href="#top">▲ 目次へ</a></div>

裏の処理がどこまで進んだかを、セッションごとに記録する。

| 項目 | 値 | 意味 |
|---|---|---|
| `status` | `processing` | 処理中 |
| | `ready` | 終わって、次へ進める |
| | `error` | 失敗した |
| `complete_stage` | `new_chat`／`prepare`／`main_chat`／`mob_chat`／`after` | どの段階の話か |
| `error_stage` | `world`／`character` など | 失敗した場所 |
| `error_message` | | 失敗の内容 |
| `progress_done`、`progress_total` | 数 | 初期記憶の段階のうち、終わった数と全部の数 |
| `progress_label` | 文字列 | 今やっている段階（例: `世界の記憶`、`白井　結: 分類`、終われば `完了`） |
| `needs_mob_chat`、`mob_count`、`next_speakers` | | 複数キャラクターの会話用（未使用） |

`complete_stage` の並びは、1回の発言を「前処理 → 本処理 → モブの発言 → 後処理」に分けて順に進める設計を表している。

| 値 | 段階 |
|---|---|
| `new_chat` | 新規チャット（初期記憶の生成） |
| `prepare` | 発言の前処理 |
| `main_chat` | 返答の生成 |
| `mob_chat` | 他のキャラクターの発言 |
| `after` | 発言の後処理（記憶の更新など） |

今のコードが実際に書き込むのは次のとおり。

| 時点 | `status` | `complete_stage` |
|---|---|---|
| `/new_chat` を受けた直後 | `processing` | `new_chat` |
| 世界とキャラクターの記憶が全部できた | `ready` | `new_chat` |
| 世界・キャラクターの記憶で失敗 | `error` | `new_chat`（`error_stage` に `world` か `character`） |
| `/chat` を受けた直後 | `processing` | `main_chat` |
| 返事（と掛け合い）ができた | `ready` | `main_chat` |
| 発言のあと、キャラクターの記憶の更新を始めた | `processing` | `after` |
| パーティー・その場の参加者・あらすじ・キャラクターの記憶の更新が全部できた | `ready` | `after` |
| キャラクターの記憶の更新で失敗（その人の記憶は前のまま） | `error` | `after`（`error_stage` に `character`） |
| パーティー・その場の参加者・あらすじの更新だけで失敗（それは前のまま。キャラクターの記憶は更新する） | `error` | `after`（`error_stage` に `world`） |

- `status` の意味: `processing` は作成中、`ready` は完了、`error` は失敗。初期記憶では、世界の記憶とキャラクターの記憶が
  全部できてから `ready` になる（世界の記憶ができても、キャラクターの記憶を作っている間は `processing` のまま）。
- 世界の記憶で失敗したら、そこで止める（キャラクターの記憶には進まない）。`error_stage` には、失敗した場所（`world`）が残る。
- 初期記憶の進み具合: 全部の段階の数は「世界の記憶(1) + メインキャラクター1人につき8段階」。
  段階を始めるたびに `progress_done`（それまでに終わった数）と `progress_label` を書き、全部できたら
  `progress_done` = `progress_total`、`progress_label` = `完了` にする。
- 画面は `/session_status` でこれを読み、入力欄の上にプログレスバーを出す。失敗したら、バーの代わりに
  失敗した場所（世界の記憶／キャラクターの記憶）を赤字で出す。

<a id="s7"></a>

## 5. 発言する（`/chat`）

<div align="right"><a href="#top">▲ 目次へ</a></div>

1. 画面は、入力欄の内容を自分の吹き出しとしてチャット欄に足し、選択中のセッションIDと一緒に送る。送信中は「発言」ボタンを押せなくする。
2. サーバーは、進行状態を `processing` / `main_chat` にする。
3. 返事と、あれば掛け合いを作る（下の「発言1回分の流れ」の 1〜4）。
4. 進行状態を `ready` / `main_chat` にする。
5. プレイヤーの発言・返事・掛け合いを、この順で履歴に足して保存し、裏でキャラクターの記憶の更新を始める。
6. 画面は、返ってきた返事と掛け合いを順に吹き出しとして足し、記憶の更新が終わるまで「発言」を止める。

- 返答の生成に失敗した場合、履歴には何も足さない。画面にはエラーが出る。
- 失敗した発言は、画面からも自分の吹き出しを消し、文章を入力欄に戻す（もう一度「発言」を押せば送り直せる）。
  待っている間に入力欄へ打った文があれば、戻した文の後ろに残す。

<a id="s7-1"></a>

### 1回の発言でやること

<div align="right"><a href="#top">▲ 目次へ</a></div>

| 段階 | やること |
|---|---|
| 本処理（`02_main/`） | 会話（返答の生成）と、会話ログの保存 |
| 後処理（`03_postprocess/`） | その会話による状態の更新一式（世界の記憶、キャラクターの記憶・所持品、パラメーターの変動、要約） |

- 前処理（`01_preprocess/`）は、おそらく不要になった。
- 今あるのは、本処理と、後処理のうちその場の参加者・あらすじ・キャラクターの記憶の更新（残りは Q69。[`../status.md`](../status.md)）。

#### 発言1回分の流れ

1. **返事をする人を決める**: まず、プレイヤーの発言で**名前で呼ばれた人**を探す。いなければ「誰に向けた発言か」を判定し、言われた相手が返事をする。判定できなければ、最初のメイン。
   - **名前で呼ばれた人**: モデルには、発言の中で名前で呼びかけた・話しかけた・用事を頼んだ相手の名前を、書いてあるとおりに出てきた順で抜き出させるだけ
     （`02_main/07_query_judge_called_names.yaml`。「白井さん、宜しく。鈴木さん、問診票下さい」→ 白井、鈴木）。
     その名前が登場人物（その場にいる人）のだれに当たるかは、プログラムが表示名・名字・下の名前・IDで照らし合わせる。シナリオごとの書き分けは要らない。
     - 1つの名前が何人にも当たる（白井 → 結と圭太）ときは、メインキャラクターを優先する。メインが何人も当たる、または当たらないときは、その名前は使わない。
     - 登場人物にいない名前は使わない（新しく現れた人は、下の確認で先に登場人物に足されている）。
     - **2人以上が呼ばれたら、呼ばれた順にそれぞれが返事をする**。あとの人の材料には、先の人の返事まで入れる。このときは、相談・意識の確認・掛け合いはしない。
       返事のプロンプトには「何人かに向けた発言なら、自分に向けた部分にだけ返事をする」と書いている。
     - 1人だけ呼ばれたら、判定はせず、その人が返事をする（そのあとの相談・意識の確認・掛け合いは、今までどおり）。
     - 「誰に向けた発言か」の判定だけでは、「白井さん、〜。鈴木さん、問診票下さい」で圭太を選ぶなど、名前で頼んだ相手を外すことがあったため。
   - 判定の問い合わせ（用途 `judge`）は、答えを1つに決めるだけなので、`generation.yaml` で temperature を 0.1 にしている。
   - 判定の前に、プレイヤーの発言で呼ばれた人・話しかけられた人・用事を頼まれた人のうち、まだその場にいない人を確かめ、
     その場の参加者に足す（`02_main/00_query_judge_newcomer.yaml`）。世界設定にいない人（「鈴木さん、カルテください」の鈴木 など）は、
     ここで登場人物にも足す（7 と同じ足し方）。こうすると、声をかけたその発言で、その人が返事をできる。
2. **返事を作る**: そのキャラクターの記憶と、直前の会話（会話ログの最後の10行）と、プレイヤーの発言をプロンプトに詰めて送る
   （`02_main/02_query_chat.yaml`）。記憶の無い人（サブなど）は、世界の記憶の参加者（関係性）を記憶の代わりにする。
   - 返事の形は「（心情・行動）」の1行と、セリフ1〜2文。1行目には、気持ちと、その場でする動作（書き終えて差し出す など）を書く。
   - 発言の中の（ ）や ( ) で囲まれた部分は、セリフではなく、行動や時間の経過として扱う。「(問診票を書き終えるまで待っている)」のように
     時間が進むときは、その間に済むことを済ませた場面として返事をする（返事・相談・掛け合いの話しかけの3つ）。
   - **プレイヤーの（ ）の行動は、もう起きた確定の出来事**として扱い、それと食い違う返事をさせない（先生が「（問診票を受け取る）」なら、
     問診票はもう先生の手にある）。受け取ったのに、結が「問診票を胸に抱えて」書き続ける返事をしたことがあったため。
     画面には、入力欄に（ ）を入れるボタンとショートカットがある。
   - 返事のプロンプトには、会話ログの中の自分の最後の発言を「直前のあなたの発言」として渡し、同じ言葉・同じ内容を繰り返さず、話を先へ進めるよう書いている。
   - キャラクター設定は、空の項目（`null`、`0`、テンプレートのまま）を除いて送る。サブの設定はほぼ全部が空で、送っても雑音にしかならないため。
   - 「あなた自身は 白井 圭太（白井 結の夫）です。ほかの人物の立場で話さない。自分の名前で自分に呼びかけない」と、話す人を名前と職業ではっきり書く
     （返事・相談・掛け合いの話しかけの3つ）。設定がほぼ空のサブの圭太が、直前に話した結の立場で「圭太さん」と自分に呼びかけたことがあったため。
   - **2a. 相談**: 返事の前に、同じパーティーの人（下の「パーティー」）がその場にいれば、「一人で答えるか、その人に相談してから答えるか」を
     問い合わせる（`02_main/05_query_judge_consult.yaml`）。二人に関わることを聞かれた・決めることを求められたときは相談し、
     本人だけに向けた質問やあいさつ、（ ）で囲んだ行動・時間の経過だけの発言なら相談しない。相談するなら、次の順になる。
     1. 返事をする人が、相手に相談の一言をかける（`02_main/06_query_consult.yaml`。まだプレイヤーへの答えは言わない。
        プレイヤーには話しかけず、相談の相手に向けた言葉にする。「先生、それって…」と先生に向けた一言になり、
        返す側の夫が先生の代わりに答えてしまったことがあったため。返す側の返事にも「ほかの人の代わりに答えない」と書いている）
        - **宛先を判定で確かめる**: 相談の一言ができたら、「誰に向けた発言か」の判定（`02_query_judge_character_identification.yaml`。
          候補は相談の相手とプレイヤー）で確かめる。プレイヤーに向いていたら、それは相談ではなく**返事として使い**、2・3 は作らない
          （そのあとは、相談しなかったときと同じく、意識の確認と掛け合いへ進む）。プロンプトで念を押しても「先生、〜」と先生に向けることが続いたため。
     2. 相手が返す（`02_query_chat.yaml`）
     3. 返事をする人が、相談を踏まえてプレイヤーに答える（`02_query_chat.yaml`。材料の会話に、プレイヤーの発言と相談のやり取りを入れる）
        - この返事が、1 の相談の一言とまったく同じなら、出さない（同じ文が2回並んだことがあったため）。

     相談したときは、もう相手と話したので、意識の確認（3）と掛け合い（4）はしない。相談の確認や相談で失敗したときは、相談せずに返事をする。

     ```
     究也        手術と投薬の二つの方法がありますが、どうされますか？
     結          …どうしよう、あなた。                 ← 相談
     圭太        結が楽な方でいいと思うよ。
     結          では、投薬でお願いします。             ← プレイヤーへの返事
     ```
3. **意識を確かめる**: 返事のあと、そのキャラクターの意識が今だれに向いているかを、短く問い合わせる
   （`02_main/03_query_judge_attention.yaml`。登場人物からIDで答えさせる）。答えは記憶には書かない（記憶は 9 で更新する）。
   **返事をした相手と、意識が向いている相手は同じとは限らない**（医師に返事をしていても、夫の手を握って不安なら、意識は夫）。
   そのため、これまでの会話に加えて、直前までの記憶（意識・心情・行動。記憶の無い人は関係性）も渡して判断させる。
   - **相談・意識の確認・掛け合い（2a・3・4）は、メインキャラクター（`参照種別` が `character`）が返事をするときだけ行う。**
     サブや途中から来た人が返事をするときは、返事の1行で終わる（例: 「鈴木さん、問診票を持ってきてください」→ 鈴木「はい、先生。白井様の分を持ってきました。」で終わり）。
     サブ同士の掛け合いは、どちらに話を戻すかなどをプログラムで細かく操ることになり、不自然になりやすいため。
4. **掛け合い**: 意識がプレイヤー以外（サブキャラクターなど）に向いていれば、その2人の掛け合いを**1往復**だけ自動で作る。
   掛け合いの相手は、**同じパーティーの人だけ**（意識が別のパーティーの人や、パーティーに入っていない人に向いていたら、掛け合いはしない）。
   返事をした人がどのパーティーにも入っていないときは、相手を絞らない。
   返事をしたキャラクターが相手に一言かけ（`02_main/04_query_cross_talk.yaml`）、相手が返す（2 と同じ `02_query_chat.yaml`）。
   掛け合いのあとは、返事をしたキャラクターが**プレイヤーに向き直って一言かける**（`04_query_cross_talk.yaml` を、相手＝プレイヤーで使う）。
   - 話しかけのプロンプトには、自分の直前の発言（話しかけでは返事、向き直りでは話しかけ）を渡し、
     同じ言葉・同じ内容を繰り返さないこと、相手（向き直りではプレイヤー）に向けた言葉にすることを指示する
     （前に、鈴木が夫に「どうぞ、こちらへお座りください」と言い、向き直りでも先生に同じ文を言ったことがあったため）。
   意識がプレイヤーに向いていれば、掛け合いは作らない。意識の確認や掛け合いで失敗したときは、掛け合いを無しにして、返事までは返す。

   ```
   プレイヤー          いらっしゃいませ
   メインキャラクター  はーい
   メインキャラクター  ね、いこ？            ← 意識がサブキャラクターに向いていたので、掛け合い
   サブキャラクター    うん
   メインキャラクター  先生、お願いします    ← プレイヤーに向き直る
   ```

   サブキャラクターは、キャラクター設定がほぼ無い。世界の記憶にある関係性（参加者の情報）を元に話させる。
5. **会話ログに保存する**: プレイヤーの発言、返事、掛け合いを、この順で履歴に足す。次の発言で、直前のやり取りが材料に要るため。
6. **画面に返す**: 返事と掛け合いをまとめて返し、画面は順に吹き出しにする。
7. **裏で「パーティー」と「その場の参加者」を更新する**: この順で行う（その場の参加者を更新するときに、更新したパーティーで一緒に動かすため）。
   - 先に、**パーティー一覧**（下の「パーティー」）を今回の会話に合わせて更新する（`03_postprocess/01_query_update_party.yaml`）。
     一緒に行動すると決まった人どうしは組にし、別行動になった人は外し、1人だけになった組は消す。
     **プレイヤーも入る**（往診に同行する、ついて来る など。プレイヤーと同じ組の人が「連れ」）。
     メンバーは登場人物にいる人だけにする（見つからない人は外す。今回の会話で新しく現れた人は、まだ登場人物にいないので、次の発言のあとで入る）。
   - 続けて、世界の記憶の「現在の状態 → 参加者」（今その場にいる人）を、今回の会話に合わせて更新する
     （`03_postprocess/01_query_update_world_memory.yaml`）。来た人・呼ばれて現れた人は足し、出て行った人は外す。プレイヤーは常にいる扱いで、一覧の先頭に入れる。
   - **パーティーの人は一緒に出入りする**: 出て行った人・来た人と同じパーティーの人（プレイヤーは除く）も、一緒に外す・足す（コードで行う）。
     「結だけ席を外した」のような別行動は、先のパーティーの更新で組が分かれるので、結だけが外れる。
   - **プレイヤーが場所を移ったら、連れだけがついて来る**: モデルに「プレイヤーの移動」（プレイヤー自身が別の場所へ移ったか）も答えさせ、
     移ったなら、その場の参加者を「プレイヤーと同じパーティーの人 ＋ 移った先で来た人」に入れ替える。
     例: 究也が結を連れて往診に出る → 圭太と鈴木は残り、その場は究也と結になる。
   - モデルには**「来た人」と「出て行った人」だけを答えさせ**、書かれなかった人はそのまま残す。全員の一覧を書かせると、今回の会話で話した人だけを書いて、ほかの人を落とすことがあるため（出入りが無いのに白井夫妻が消え、結が「患者さん」として別人で足されたことがあった）。
     今の参加者は、登場人物とIDか名前で照らし合わせて残す（見つからない人は外す）。
   - 世界設定にいない人が新しく現れたら（突然声をかけた友人など）、そのセッションの登場人物に足す。ID は `guest_1`、`guest_2`… と振り、
     `参照種別` は `inline`、`役割` は `sub`、`職業` にはその人の立場（プレイヤーの友人 など）を入れる。名前と立場だけの設定YAML
     （`character/{ID}_setting.yaml`）を作り、世界の記憶の「世界の状態 → 参加者」にも入れる。Web側の世界設定（元のファイル）は変えない。
   - **返事をする人の判定・意識の確認・掛け合いの相手・記憶の更新は、その場にいる人だけで行う**（部屋を出て行った人は返事をしない）。
     世界の記憶がまだ無い、または誰もいないときは、登場人物全員を候補にする。
8. **裏で会話のあらすじを更新する**: 「今のあらすじ ＋ 今回の会話 → 新しいあらすじ」を問い合わせ（`03_postprocess/01_query_update_story_summary.yaml`）、
   セッションフォルダの `summary.yaml`（`あらすじ:` の箇条書き）に保存する。
   - 返事の材料には会話ログの最後の10行しか入れないので、それより前の話の要点（決まったこと、約束、分かった名前や関係、打ち明けた悩み、出来事）をここに残す。
   - 全体で15項目までに保ち、超えるときは古い項目どうしをまとめる。
   - 返事（2）と、相談・掛け合いの話しかけ（2a・4）のプロンプトに、「これまでのあらすじ」として入れる。
9. **裏でキャラクターの記憶を更新する**: その場にいる、記憶のあるメインキャラクターごとに、「今の記憶 ＋ 今回の会話（プレイヤーの発言から最後まで）
   → 更新した記憶」を問い合わせ（`03_postprocess/02_query_update_character_memory.yaml`）、`character/{ID}_memory.yaml` を書き換える。
   - 新規チャットの作成をやり直すのではなく、今の記憶を会話に合わせて書き換える（作り直すと、材料が開始メッセージなので会話が入らない）。
   - `関係性` は、前からいる人を消さず、今回の会話で初めて会った人（直接話した人）だけを足す（モデルが書き落としても、前の人は残す）。
   - `所持品` は、今その人が持っている物。会話や行動から、手に持っている・使っている・受け取った物が分かれば足し
     （「渡した」という言葉が無くても、問診票に記入していれば問診票を足す）、渡した・置いてきた・なくした物は外す。着ている服は `服装` に書く。
     プレイヤーの（ ）の行動で受け渡しがあれば、それを正として所持品を直す（ほかの人の発言や行動と食い違っても、プレイヤーの行動を優先する）。
     画面の「持ち物」は、これを出す。
   - 返事を記憶として読めなければ、その人の記憶は前のまま残し、失敗として記録する。
   - 記憶の更新に渡すのは `現在の状態` だけ。続けて、**抱えている事情**（悩み・事情、目的・願い、秘密、大事な出来事、約束・予定）を、
     「今の事情 ＋ 今回の会話 → 更新した事情」で別に問い合わせて更新する（`03_postprocess/02_query_update_character_concerns.yaml`）。
     新しく分かったこと・決まったことは足し、解決した悩み・果たした約束・もう秘密でなくなったことは外す。
     1つの項目は10件まで。超えるときは、古いもの・似たものを1つにまとめさせる（念のため、プログラムでも新しい方の10件に切る）。
     進み具合は「パーティー・その場の参加者・あらすじ ＋ 1人につき2段階（記憶の更新・抱えている事情）」。
   - **あらすじとの違い**: あらすじは、そのセッションで起きたことを外から見た話の流れ（みんなで共有）。抱えている事情は、その人の内側から見たもので、
     思い込みや、話す前からの過去、秘密も入る。あらすじとずれていてよい。
   - 抱えている事情は、記憶と一緒に、返事・相談・掛け合いの話しかけ・意識の確認の材料に毎回入る。返事などのプロンプトには
     「秘密は、自分から人に話さない（話すと決める流れになったときだけ話す）」と書いている。
     送る長さが増えるので、一度に扱える長さ（`local_model_n_ctx`）を 8192 にしている（4096 だと、事情を足すとあふれる恐れがあった）。
   - 進行状態は `complete_stage` = `after`。新規チャットと同じく、終わるまで画面は「発言」を止め、プログレスバーを出す。
10. **裏で画像を作る（入口だけ）**: 記憶の更新と並べて、画像作成の別スレッドを起こす（`services/image/image_generation.py`）。
   今は何もしない。中身は、画像生成の連携（Q37）を作るときに入れる。

- **パーティー**: 世界の記憶の「現在の状態 → パーティー一覧」（白井夫妻 など、一緒に行動している人のまとまり）。
  「その場の参加者」は今その場にいる人、「世界の参加者」はこれまでに出てきた人全員で、パーティーは**相談し合い、掛け合い、一緒に動く単位**として使う。
  - 相談の相手（2a）と掛け合いの相手（4）は、同じパーティーで、その場にいる人に限る（プレイヤーは相手にしない）。
    そのため、結が「究也と結」の組だけに入っていると、圭太とは掛け合わない（結と圭太の両方が連れなら、3人の組になる）。
  - 意識の確認（3）と相談の確認（2a）のプロンプトに、パーティー一覧を渡す。
  - 新規チャットの初期記憶で作り、発言のあとに更新する（上の 7）。同じ組の人は一緒に出入りし、プレイヤーが場所を移ると連れだけがついて来る（上の 7）。
- **【要確認 Q76】** 掛け合いを、プログラムで1手ずつ決める今の作りではなく、「返事のあと、その場の人たちが続けて何を言うか（話す人の名前つき0〜3行）」を
  1回の問い合わせでまとめて書かせる作りにするか。場面に合った流れになりやすく、決まりをコードで増やさずに済む一方、
  今のモデルの大きさでは各キャラクターの性格や記憶を守りきれない恐れがある。大きなモデル（OpenRouter など）を使うときに試す。
- **判定プロンプト**（`02_main/02_query_judge_character_identification.yaml`）: 「キャラクターAの発言」に対する「キャラクターBの回答」が
  誰に向けたものかを、候補の中からIDで答えさせる。
  - 発言のときは、A = 直前の発言（履歴の最後の行）、B = プレイヤーの発言、候補 = プレイヤー以外の登場人物（`ID（表示名）` の形で並べる）。
  - 名前を呼んで話しかけた人（「鈴木さん、〜」）や、用事を頼んだ相手（「〜ください」）がいれば、その人を優先させる
    （「まぁそう緊張なさらず。鈴木さん、問診票ください」で、鈴木ではなく圭太を選んだことがあったため）。
  - 答え（`target_speakers: ID`）が候補のIDか表示名に合えば、その人が返事をする。`unknown`・`null`・候補に無い名前なら、最初のメイン。
  - 登場人物は、セッションに写した世界設定の「世界の登場人物」から作る（`helpers/session_cast.py`）。名前を直書きしない。
- **登場人物の書き方**: 判定・意識の確認・返事・掛け合い・記憶の更新のプロンプトには、登場人物を「ID（表示名・職業）」の形で渡す
  （例: `kyuya（究也・カッコウ医院の先生）`）。職業は世界設定の登場人物の `職業`。
  会話の中の呼び方（「先生」など）と人物を結び付けられないと、意識の確認や記憶の「意識」が正しく決まらないため。
- **発言者は実際の人物にする**（固定の名前を使わない）。登場人物は `helpers/session_cast.py` が、セッションの世界設定から読む。
  | 発言 | 発言者 |
  |---|---|
  | 開始メッセージ | 最初のメインキャラクター（`参照種別` が `character` の最初の人。いなければプレイヤー以外の最初の人） |
  | プレイヤーの発言 | 世界の登場人物の `player`（履歴の `role` は `player`） |
  | 返事 | 判定で選んだ人（履歴の `role` は `main`） |
  | 世界の記憶の「プレイヤーID」「プレイヤー名」 | 世界の登場人物の `player` |
- 表示名は、世界設定の `表示名`。無ければ、セッションに写した設定YAMLの `名前` → `表示名`、それも無ければID。

- 発言のあとに更新するのは、その場の参加者・あらすじ・キャラクターの記憶（上の流れの 7〜9）。ほかの更新は、次の【要確認】で決める。
- **【要確認 Q69】** シナリオパラメータ（好感度など）の、会話による増減を作るか（`03_postprocess/01_query_parameter_fluctuation.yaml` がある）。

## 8. チャット画面の画像

<div align="right"><a href="#top">▲ 目次へ</a></div>

- アイコン: 吹き出しを作るたびに、`/session_image/{セッションID}/icon/{発言者のID}` から読む。無ければ名前の頭文字を出す。
- 立ち絵: 吹き出しかアイコンをクリックすると、その発言者の立ち絵を `/session_image/{セッションID}/standing/{発言者のID}` から読んで、中央の欄に出す。
  無ければ欄を初期表示に戻す。
- どちらも、新規チャット時にセッションへ退避した画像。システムのメッセージと、画像の無い人（サブ、会話で現れた人）は頭文字を出す。
- **【要確認 Q37】** 立ち絵は「クリックしたら出る」。新しい返答が来たときに、その発言者の立ち絵へ自動で切り替えるのが本来の形か
  （欄の名前は「発言キャラクター立ち絵」）。
  - 画像生成の連携を作るときの条件（2026-10-24 にユーザーと確認）:
    - **VRAM**: サブPCの GPU は 24GB。チャットのモデル（`local_model_name`）だけで、今は約 16GB を使っている。
      今使っている画像のモデルなら、チャットのモデルと一緒に載せて動くことは、ユーザーが確かめ済み。
      重い画像のモデル（FLUX.1 Kontext など）を使うなら、画像を作る間だけチャットのモデルを降ろすなどの切り替えが要る。
    - **絵柄の安定**: 画風とキャラクターの見た目（設定YAMLの外見から作るタグ、LoRA、参照画像）は固定の文にし、
      場面・表情・ポーズだけを会話から変える形が向いている。キャラクターのLoRAは、ユーザーが作りかけ
      （服のワッペンや袖のような細部が、ポーズを変えるたびに崩れるのが課題）。
    - **画像のモデルの方針**: まずは SDXL 系のアニメ向けモデル（7GB 前後。Illustrious・NoobAI 系など）で作る。
      会話の場面は、チャットのモデルに Danbooru 風のタグへ変換させてプロンプトにする。
      FLUX・Qwen-Image などの新しい大きいモデル（16〜40GB。軽くした版でも 12GB 前後）は、自然な文章が通り、
      2人以上が絡む構図や手・文字に強いが、1人の立ち絵・表情差分ならタグで足りる。2人以上が絡む場面の絵がどうしても要るときに考える。
